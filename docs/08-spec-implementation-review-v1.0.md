# 병동 근무표 서비스 명세·구현 비교 및 개선안

| 문서 정보 | 내용 |
| --- | --- |
| 버전 | 1.0 |
| 검토 대상 | 기능명세서 v1.0, API 명세서 v1.0, 기능 DB, 현재 프론트엔드와 백엔드 |
| 검토 관점 | 업무 적합성, 데이터 일관성, 보안, 운영 안정성, 사용자 흐름, 테스트 가능성 |

## 1. 종합 결론

현재 구현은 API 라우트와 데모 사용자 흐름을 확인하는 MVP로는 의미가 있다. API 명세에 정의된 59개 엔드포인트는 대부분 실제 라우트와 서비스 메서드로 연결되어 있고, 다음 핵심 흐름은 동작한다.

```text
회원가입
→ 로그인
→ 병동 개설 또는 가입 신청
→ 간호사 등록
→ 근무 신청과 승인
→ 월 근무표 생성
→ 자동 생성
→ 결과 조회와 셀 수정
→ 근무표 확정
```

그러나 API가 존재하는 것과 명세의 업무 규칙이 완성된 것은 구분해야 한다. 규칙 설정, 자동 생성 실패·중단, 통계, 공휴일·OFF 목표, 감사 로그, 알림 설정 등은 API 형식만 존재하거나 축약 구현되어 있다.

### 최종 판정

| 영역 | 판정 |
| --- | --- |
| API 경로 | 대체로 구현 |
| 핵심 관리자 데모 | 동작 가능 |
| 일반 간호사 전체 흐름 | 미완성 |
| 업무 규칙 준수 | 부분 구현 |
| 자동 생성 신뢰성 | 프로토타입 수준 |
| 통계·공정성 | 미구현 |
| 감사·알림 | 부분 구현 |
| 운영 투입 가능성 | 현재 상태로는 부적합 |

## 2. 잘 구현된 부분

### 2.1 병동 범위 접근 통제

- 병동 리소스가 `/wards/me` 아래에 구성되어 있다.
- 서버가 사용자의 소속 병동을 기준으로 데이터를 조회한다.
- 일반 간호사는 DRAFT 근무표를 조회할 수 없다.
- 일반 간호사 응답에서 경력, 숙련도, 건강 상태 등의 민감 필드를 제거한다.

판정: **현재 구현 유지**

### 2.2 기본 인증 보안

- 비밀번호를 PBKDF2로 해시한다.
- 세션 원문 대신 해시를 데이터베이스에 저장한다.
- 변경 요청에 CSRF 토큰을 검사한다.
- 운영 모드에서 Secure 쿠키, CORS 허용 목록, 데모 인증 차단을 사용한다.
- 로그인 요청 횟수를 제한한다.

판정: **현재 구현의 방향 유지, 인증 계약 문구 조정**

### 2.3 동시성 및 중복 실행 방지

- `Idempotency-Key`를 저장하고 같은 요청 결과를 재사용한다.
- 같은 키의 다른 본문은 거절한다.
- 근무표 셀 변경에 `baseVersion`을 적용한다.
- 편집 잠금 API와 잠금 토큰 검사가 있다.
- 셀 일괄 변경과 Excel 반영을 트랜잭션으로 처리한다.

판정: **현재 구현 유지**

### 2.4 신청 기본 흐름

- 과거 날짜 신청을 거절한다.
- 신청 날짜가 같은 월인지 검사한다.
- 소속 기간 밖 신청을 거절한다.
- 확정 근무표 날짜의 신청을 거절한다.
- 같은 날짜의 PENDING·APPROVED 신청 충돌을 차단한다.
- 승인된 연차를 AL로 반영한다.
- 승인된 희망 휴무는 인력이 충분할 때 O가 되도록 우선순위를 조정한다.

판정: **현재 구현을 기반으로 확장**

### 2.5 운영 기본 장치

- `/health`, `/ready` 상태 확인이 있다.
- 운영 환경의 구조화 로그를 지원한다.
- Docker 실행 구성이 있다.
- SQLite 백업과 무결성 검사 스크립트가 있다.

판정: **현재 구현 유지, 복구 훈련과 모니터링 추가**

## 3. 우선순위별 핵심 차이

## 3.1 P0 — 운영 전에 반드시 수정

### P0-01 규칙 설정이 실제 자동 생성에 적용되지 않음

#### 명세

- 규칙 활성 여부, 강도, 임계값을 변경할 수 있다.
- 규칙 변경은 다음 검증과 자동 생성에 적용된다.
- 필수 HARD 규칙은 비활성화할 수 없다.

#### 현재 구현

- 규칙 값은 데이터베이스에 저장된다.
- 위반 검사와 생성기는 저장된 규칙을 읽지 않고 고정 코드로 동작한다.
- 모든 규칙을 비활성화하거나 SOFT로 바꿀 수 있다.
- 규칙 변경 응답의 영향 요약은 항상 빈 배열이다.

#### 판단

**명세가 더 적합하다.** 설정 화면과 실제 결과가 다르면 사용자가 잘못된 근무표를 신뢰하게 된다.

#### 개선

- 규칙 코드별 검증기 인터페이스를 만든다.
- 활성 규칙과 파라미터를 병동별로 로딩한다.
- 검증기와 생성기가 동일한 규칙 정의를 사용한다.
- 법정·건강 보호 규칙은 API에서 비활성화를 거절한다.
- 규칙 변경 후 영향받는 DRAFT 근무표를 재검사한다.

### P0-02 자동 생성이 하드 위반을 남기고도 성공 처리됨

#### 명세

- 하드 위반 0건인 결과만 성공이다.
- 유효한 해가 없으면 `NO_SOLUTION`으로 처리한다.
- 충돌 원인, 완화안, 부분 결과를 제공한다.

#### 현재 구현

- 생성 후 하드 위반 수를 계산하지만 상태는 항상 `SUCCEEDED`로 저장한다.
- `conflicts`, `relaxations`는 빈 배열이다.
- 부분 결과 API는 별도 부분 해를 적용하지 않는다.

#### 판단

**명세가 더 적합하다.** 하드 위반이 있는 근무표를 성공으로 표시하면 안전성과 신뢰성이 훼손된다.

#### 개선

- 하드 위반이 1건 이상이면 `NO_SOLUTION`으로 종료한다.
- 충돌 규칙과 영향을 받는 날짜를 저장한다.
- 현재 최선 결과는 확정 근무표와 분리된 작업 결과로 보관한다.
- 사용자가 부분 결과를 명시적으로 선택할 때만 DRAFT에 적용한다.

### P0-03 자동 생성 중단이 실제 작업을 중단하지 않음

#### 현재 구현

- API는 작업 상태를 `STOPPED`로 바꾼다.
- 실행 중인 백그라운드 스레드는 중단 플래그를 확인하지 않는다.
- 중단 이후 스레드가 결과를 다시 저장할 수 있다.

#### 판단

**명세가 더 적합하다.**

#### 개선

- 작업별 취소 토큰 또는 DB 취소 플래그를 둔다.
- 생성기는 일정 단위마다 취소 여부를 확인한다.
- `STOPPED` 작업이 결과를 덮어쓰지 못하도록 조건부 UPDATE를 사용한다.
- 운영 환경에서는 프로세스 내부 스레드 대신 작업 큐 사용을 검토한다.

### P0-04 수간호사 권한 이관이 원자적이지 않음

#### 명세

- 대상 승격과 기존 수간호사 강등을 하나의 트랜잭션으로 처리한다.
- 작업 후 최소 한 명의 수간호사가 남아야 한다.

#### 현재 구현

- 대상 승격 메서드가 먼저 별도 트랜잭션으로 완료된다.
- 이후 기존 수간호사를 다른 트랜잭션에서 강등한다.
- 권한 변경 감사 로그가 없다.

#### 판단

**명세가 더 적합하다.**

#### 개선

- 승격과 강등을 하나의 서비스 트랜잭션으로 합친다.
- 대상의 활성 상태와 연결 계정을 검사한다.
- 변경 전후 권한을 감사 로그에 기록한다.

### P0-05 감사 로그에 민감한 자유 입력이 포함될 수 있음

#### 명세

- 민감한 자유 입력은 감사 로그에 저장하지 않는다.

#### 현재 구현

- 근무 신청의 감사 데이터에 `reasonDetail`이 포함될 수 있다.

#### 판단

**명세가 더 적합하다.** 연차·건강 관련 사유는 민감정보가 될 수 있다.

#### 개선

- 감사 로그 전용 직렬화 모델을 만든다.
- 신청 종류, 날짜, 상태만 기록하고 자유 입력은 제외한다.
- 기존 감사 데이터의 보존·마스킹 정책을 정한다.

## 3.2 P1 — 핵심 기능 완성을 위해 수정

### P1-01 빈 근무표가 실제 셀을 만들지 않음

#### 명세

- 월 근무표 생성 시 간호사와 날짜 셀을 준비한다.
- 소속 기간 밖 셀은 비활성화한다.
- 승인된 연차를 AL로 표시한다.

#### 현재 구현

- Schedule 레코드만 만들고 null 셀을 만들지 않는다.
- 승인 연차가 근무표보다 먼저 존재하면 자동 생성 전까지 AL이 표시되지 않는다.
- 프론트는 없는 셀을 소속 기간 밖 셀처럼 편집 불가로 처리한다.

#### 판단

**명세가 더 적합하다.**

#### 개선

- 조회 시 가상 셀을 구성하거나 생성 시 전체 null 셀을 저장한다.
- 권장안은 조회 응답에서 전체 셀 매트릭스를 구성하고 실제 값만 저장하는 방식이다.
- 승인된 연차는 조회 응답과 저장 데이터 모두 AL로 일관되게 반영한다.

### P1-02 승인된 신청을 취소할 수 없음

#### 명세

- 근무표 확정 전이라면 승인 신청도 취소할 수 있다.
- 연차 또는 선호 제약을 초안에서 제거하고 재검증한다.

#### 현재 구현

- `PENDING` 신청만 취소 가능하다.

#### 판단

**명세가 더 적합하다.** 실제 병동에서는 승인 후 일정 변경이 발생할 수 있다.

#### 개선

- `APPROVED → CANCELLED` 전이를 추가한다.
- 확정된 월은 취소를 차단한다.
- 연차 취소 시 AL을 null로 복원하고 기존 자동 배정 결과를 임의로 채우지 않는다.
- 희망 신청 취소 시 제약만 제거하고 재생성 필요 상태를 표시한다.

### P1-03 수간호사 직접 등록 간호사와 가입 계정이 중복될 수 있음

#### 필요한 업무 흐름

- 수간호사가 계정 없는 간호사를 먼저 등록할 수 있어야 한다.
- 해당 간호사가 나중에 회원가입하면 기존 프로필과 연결해야 한다.

#### 현재 구현

- 직접 등록 Nurse는 임의 UUID를 사용한다.
- 가입 승인 Nurse는 User ID를 Nurse ID로 사용한다.
- 두 프로필을 연결하는 `userId` 필드와 승인 UI가 없다.
- 같은 이름의 간호사가 중복 생성될 수 있다.

#### 판단

**명세와 구현을 모두 보완해야 한다.** 기존 명세도 계정 연결 규칙을 충분히 정의하지 않았다.

#### 개선

- `nurses.user_id nullable unique` 필드를 추가한다.
- 가입 승인 시 미연결 Nurse 후보를 반환한다.
- 기존 프로필 연결 또는 새 프로필 생성을 수간호사가 선택한다.
- 이름만으로 자동 병합하지 않는다.
- 연결 행위를 감사 로그에 기록한다.

### P1-04 개인 통계와 공정성 API 미정의·미구현

#### 기능명세

- 개인별 D/E/N/O, 목표 OFF, 주말·공휴일 근무 수를 P1로 요구한다.

#### API 명세와 구현

- 별도 통계 API가 없다.
- Schedule의 `statistics` 구조가 정의되지 않았다.
- 프론트 통계 서비스는 항상 빈 결과를 반환한다.

#### 판단

**기능명세의 방향은 적합하지만 API 명세와 구현을 함께 수정해야 한다.**

#### 개선

- `GET /wards/me/schedules/{id}/statistics`를 추가한다.
- 수간호사는 전체, 일반 간호사는 본인 데이터만 반환한다.
- 통계 필드와 공정성 지표 계산식을 명세에 확정한다.

### P1-05 공휴일과 OFF 목표가 생성·통계에 미반영

#### 현재 구현

- 공휴일과 OFF 목표를 저장하고 조회할 수 있다.
- 자동 생성과 통계 계산은 값을 사용하지 않는다.
- 기본 OFF 목표는 실질적으로 고정값 8에 가깝다.

#### 판단

**명세가 더 적합하다.**

#### 개선

- 공휴일 변경 시 통계와 목표 OFF를 재계산한다.
- OFF 목표를 생성기의 SOFT 제약으로 전달한다.
- 평일·주말·공휴일 필요 인원 정책을 확정하고 설정으로 분리한다.

### P1-06 규칙 중 일부가 누락됨

현재 위반 검사에서 부족한 항목은 다음과 같다.

- 프리셉터와 담당 신입의 동일 근무
- 목표 OFF 부족·초과
- 희망 신청 미반영
- 근무별 배정 편차
- 주말·공휴일 편차
- 일반 연속 근무 상한

판단: **명세를 따르되 규칙별 강도와 계산식을 먼저 확정해야 한다.**

### P1-07 감사 로그 기록 대상 누락

현재 누락된 주요 작업은 다음과 같다.

- 로그인·로그아웃
- 가입 승인·반려
- 수간호사 추가·이관
- 근무표 확정 취소
- Excel 내보내기
- 규칙 프리셋 적용
- 공휴일·OFF 목표 변경

판단: **명세가 더 적합하다.**

### P1-08 알림 설정이 실제 발송에 적용되지 않음

#### 현재 구현

- 알림 설정 조회·수정 API가 있다.
- 알림 생성 함수는 사용자의 설정을 확인하지 않는다.
- 근무 전날 알림과 웹 푸시는 없다.

#### 판단

**명세가 더 적합하다.** 단, 웹 푸시는 P2로 유지해도 된다.

### P1-09 ARCHIVED 전이가 없음

#### 현재 구현

- 상태 열거형과 조회 권한에는 `ARCHIVED`가 있다.
- 실제로 CONFIRMED를 ARCHIVED로 변경하는 로직은 없다.

#### 판단

**명세가 더 적합하다.** 보관 기준 월과 전환 시점을 정책으로 확정해야 한다.

## 3.3 P2 — 운영 편의와 완성도 개선

### P2-01 Excel 내보내기 내용 부족

현재 파일은 간호사, 날짜, 듀티 값 중심의 단순 xlsx이다. 명세가 요구하는 커버리지, 개인 통계, 듀티 색상, 인쇄 형식과 내보내기 감사 로그가 없다.

판정: **명세가 더 적합하다.**

### P2-02 가입 코드 방어 부족

- 가입 코드 길이와 문자 구성을 엄격히 검사하지 않는다.
- 가입 코드 시도 횟수 제한이 없다.
- 코드 활성·만료 상태 모델이 없다.

판정: **명세가 더 적합하다.** 계정당 시간당 제한을 추가한다.

### P2-03 신청 정책값 미구현

- 신청 마감일
- 연차·희망 휴무 월 한도
- 운영 가능한 사유 코드 목록

명세에는 정책 설정을 따른다고 되어 있으나 정책 데이터 모델과 API가 없다.

판정: **명세와 구현을 함께 수정해야 한다.** 정책 관리 주체와 기본값부터 결정한다.

### P2-04 정렬과 대량 목록 UI 부족

- API 문서에는 `sort`가 있지만 대부분 구현에서 무시한다.
- 프론트는 최대 100건을 가져오고 페이지 이동 UI가 없다.

판정: **명세에 맞춰 구현을 보완한다.**

### P2-05 편집 잠금 운영 동작 부족

- 잠금은 일정 시간이 지나면 만료되지만 활동 시 만료 시간이 연장되지 않는다.
- 저장 완료 시 자동 해제되지 않는다.
- 강제 인수 시 기존 사용자에게 알리지 않는다.

판정: **명세가 더 적합하다.**

### P2-06 업로드 보안 검사 부족

- 크기와 기본 형식 검사는 있다.
- 악성 파일 검사는 없다.
- 운영 환경에서 압축 폭탄과 비정상 XML에 대한 추가 제한이 필요하다.

판정: **명세가 더 적합하다.**

## 5. 명세서 자체의 불일치와 개선

### 5.1 통계 API 누락

기능명세에서는 개인 통계를 P1로 정의하지만 API 명세에는 조회 엔드포인트와 응답 모델이 없다.

권장: 통계 API와 권한별 필드 범위를 API 명세 v1.1에 추가한다.

### 5.2 동일 월 근무표 중복 처리

- 기능명세: 기존 표로 이동
- API 명세와 구현: `409 SCHEDULE_ALREADY_EXISTS`

권장: 서버는 409와 기존 리소스 식별자를 반환하고, 프론트가 기존 표로 이동한다. 현재 API 방식이 책임 구분에 더 적합하다.

### 5.3 인증 방식 표현

- 명세: 액세스 토큰과 리프레시 토큰 쿠키
- 구현: 서버 저장형 단일 세션 쿠키

브라우저 중심 단일 서비스라면 현재의 불투명 서버 세션이 더 단순하고 적합하다.

권장:

- 명세를 서버 세션 쿠키 방식으로 수정한다.
- `/auth/refresh`를 세션 연장 API로 명확히 정의하거나 제거한다.
- 로그인 응답 본문에 CSRF 토큰을 중복 노출하지 않고 CSRF 쿠키를 사용한다.

### 5.4 직접 등록 간호사와 사용자 계정 연결 누락

기능명세와 API 명세 모두 수간호사 직접 등록 이후 계정 연결 과정을 정의하지 않는다.

권장:

- Nurse에 nullable `userId`를 추가한다.
- 가입 승인 미리보기에서 연결 후보를 제공한다.
- 연결 API 또는 가입 승인 요청 필드 `existingNurseId`를 추가한다.

### 5.5 자동 생성 응답 모델 미정

다음 구조가 구체적으로 정의되지 않았다.

- `stage`
- `progress` 단위
- `metrics`
- `conflicts`
- `relaxations`
- 부분 결과 식별자와 만료 정책

권장: 상태별 응답 예시와 JSON 스키마를 명세에 추가한다.

### 5.6 셀 변경 응답 불일치

일부 예시는 `changedCells`를 숫자로 표현하지만 구현과 프론트 타입은 변경된 셀 배열을 기대한다.

권장: `changedCount`와 `changedCells[]`를 분리한다. 프론트 갱신을 위해 배열을 제공하는 현재 구현 방향이 더 유용하다.

### 5.7 가입 대기 본인 조회 API 누락

소속 없는 사용자는 `/me`만으로 어떤 병동에 언제 가입 신청했는지 확인할 수 없다.

권장: `GET /me/ward-membership-request` 또는 `GET /ward-membership-requests/me`를 추가한다.

## 6. 테스트 검토

### 6.1 확인된 상태

- 프론트 ESLint 통과
- TypeScript `tsc --noEmit` 통과
- 백엔드 순수 서비스 테스트 4개 통과
- HTTP 통합 테스트는 로컬 포트가 필요한 구조이며 현재 검토 환경의 포트 제한으로 재실행이 제한됨

### 6.2 테스트 범위의 문제

현재 백엔드 테스트는 총 10개 수준으로 기능명세의 P1 수용 기준을 충분히 증명하지 못한다. 프론트 컴포넌트와 브라우저 E2E 테스트도 없다.

### 6.3 반드시 추가할 테스트

#### 인증과 접근 통제

- 만료 세션
- CSRF 누락과 위조
- 다른 병동 IDOR 요청
- 일반 간호사의 관리자 API 호출
- 로그인과 가입 코드 속도 제한

#### 간호사

- 직접 등록 후 계정 연결
- 중복 연결 방지
- 다른 병동 preceptorOf 연결 거절
- 소속 기간 축소 후 기존 배정 위반
- 마지막 수간호사 퇴사·강등 방지

#### 신청

- 승인 연차의 생성 전·후 반영
- 승인 신청 취소와 AL 제거
- 확정 월 신청·취소 거절
- 신청 마감과 월 한도
- 희망 근무 반영률

#### 근무표

- 빈 셀 매트릭스와 기간 밖 셀
- AL 직접 수정 거절
- 셀 일괄 변경 전체 롤백
- 동시 version 충돌
- 잠금 소유자와 강제 인수
- 하드 위반 확정 거절
- 소프트 위반 확인 후 확정
- CONFIRMED에서 ARCHIVED 전환

#### 자동 생성

- 충분한 인력에서 하드 위반 0건
- 인력 부족 시 NO_SOLUTION
- 중단 후 결과 덮어쓰기 방지
- 고정 셀 유지
- 규칙 파라미터 변경 결과 차이
- 공휴일·OFF 목표·희망 신청 반영

#### Excel과 감사

- 잘못된 파일·크기·압축 구조
- 미리보기 전 실제 근무표 불변
- 적용 중 오류 전체 롤백
- 내보내기 화면 데이터 일치
- 감사 로그 민감정보 미포함

## 8. 출시 판단 기준

다음 조건이 충족되기 전에는 운영 완료로 판단하지 않는다.

- 저장한 규칙이 자동 생성 결과에 실제로 반영된다.
- 하드 위반이 있는 자동 생성은 성공으로 표시되지 않는다.
- 자동 생성 중단 후 백그라운드 작업이 결과를 덮어쓰지 않는다.
- 수간호사 직접 등록 간호사와 가입 계정을 중복 없이 연결할 수 있다.
- 승인된 연차와 희망 신청의 승인·취소가 근무표에 일관되게 반영된다.
- 개인 통계와 공정성 값이 서버에서 계산된다.
- 알림 설정이 실제 알림 생성에 적용된다.
- 필수 감사 대상이 기록되고 민감정보는 포함되지 않는다.
- 모든 P1 기능이 정상, 권한 오류, 입력 오류, 상태 충돌 테스트를 통과한다.
- 운영 백업의 실제 복원이 검증된다.
