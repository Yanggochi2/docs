# 병동 근무표 서비스 처리 로직

| 문서 정보 | 내용 |
| --- | --- |
| 버전 | 1.0 |
| 문서 성격 | 기능명세와 구현 검토 결과를 반영한 권장 처리 기준 |
| 대상 | 기획자, 디자이너, 프론트엔드·백엔드 개발자, QA |
| 기본 API 경로 | `/api/v1` |
| 주요 사용자 | 수간호사 `HEAD_NURSE`, 일반 간호사 `NURSE` |

## 1. 문서 목적

이 문서는 병동 근무표 서비스의 기능이 어떤 순서와 조건으로 처리되어야 하는지를 설명한다. 단순히 API 호출 순서만 나열하지 않고 다음 내용을 함께 정의한다.

- 사용자 역할별 처리 권한
- 입력값 및 상태 유효성 검사
- 데이터 변경 순서와 트랜잭션 범위
- 신청과 자동 근무표 생성의 연결 방식
- 수간호사의 간호사 직접 등록과 로그인 계정 연결 방식
- 알림 및 감사 로그 생성 시점
- 실패 시 복구해야 하는 상태

별도 표시가 없는 로직은 운영 서비스를 목표로 하는 권장 최종 로직이다. 현재 구현과 다른 부분은 비교·개선 문서에서 따로 다룬다.

## 2. 핵심 데이터 관계

### 2.1 사용자 계정과 간호사 프로필

`User`와 `Nurse`는 같은 개념이 아니다.

| 데이터 | 목적 | 생성 주체 |
| --- | --- | --- |
| User | 로그인, 신청, 알림 수신, 권한 확인 | 사용자가 회원가입 |
| Membership | 사용자가 어느 병동에 어떤 권한으로 소속되었는지 관리 | 병동 개설 또는 가입 승인 |
| Nurse | 근무표 배정에 필요한 간호사 정보 관리 | 수간호사 직접 등록 또는 가입 승인 |

권장 관계는 다음과 같다.

```text
User 0..1 ─── 1 Nurse
               └─ wardId
               └─ userId nullable
```

- 수간호사가 직접 등록한 간호사는 `userId=null`로 시작한다.
- 간호사가 나중에 회원가입하고 병동 가입을 신청하면 기존 간호사 프로필과 계정을 연결할 수 있다.
- `nurse.id`는 근무표에서 계속 사용하는 프로필 ID이다.
- 계정 연결 이후에도 기존 근무표와 통계의 `nurse.id`는 바뀌지 않는다.
- 같은 사람을 새 간호사로 중복 생성하지 않는다.

### 2.2 주요 상태

#### 가입 신청

```text
PENDING → APPROVED
PENDING → REJECTED
```

#### 근무 신청

```text
PENDING → APPROVED
PENDING → REJECTED
PENDING → CANCELLED
APPROVED → CANCELLED  # 근무표 확정 전만 허용
```

#### 근무표

```text
DRAFT → GENERATING
GENERATING → DRAFT       # 성공, 중단, 실패, 해 없음
DRAFT → CONFIRMED
CONFIRMED → DRAFT        # 확정 취소
CONFIRMED → ARCHIVED     # 다음 기준 월 근무표 확정
```

#### 자동 생성 작업

```text
QUEUED → RUNNING
RUNNING → SUCCEEDED
RUNNING → NO_SOLUTION
RUNNING → FAILED
QUEUED/RUNNING → STOPPED
```

## 3. 공통 API 처리 로직

모든 API는 다음 순서로 처리한다.

```text
요청 수신
→ traceId 생성
→ Content-Type과 본문 크기 검사
→ 입력 형식 검사
→ 로그인 세션 확인
→ 상태 변경 요청의 CSRF 토큰 검사
→ 요청자의 활성 병동 소속 확인
→ 역할 권한 확인
→ 대상 데이터와 요청자 병동 일치 확인
→ 업무 규칙 및 현재 상태 검사
→ 트랜잭션으로 데이터 변경
→ 필요한 알림과 감사 로그 생성
→ 표준 응답 반환
```

### 3.1 공통 보안 원칙

- 역할과 병동 ID는 클라이언트 입력을 신뢰하지 않고 세션과 소속 정보에서 판정한다.
- 다른 병동 리소스는 존재 여부가 드러나지 않도록 `404`를 반환한다.
- 일반 간호사에게 타인의 경력, 숙련도, 건강 상태, 신청 사유, 개인 통계를 반환하지 않는다.
- 비밀번호는 단방향 해시로 저장한다.
- 인증 쿠키는 `HttpOnly`, `Secure`, `SameSite` 정책을 사용한다.
- 비밀번호, 세션 토큰, 전체 업로드 파일, 민감한 자유 입력은 로그에 저장하지 않는다.

### 3.2 중복 및 동시성 처리

- 생성·승인·확정·자동 생성 시작 요청은 `Idempotency-Key`를 지원한다.
- 같은 키와 같은 요청은 기존 처리 결과를 반환한다.
- 같은 키로 다른 요청을 보내면 `409 IDEMPOTENCY_KEY_REUSED`를 반환한다.
- 근무표 변경은 `baseVersion`을 검사한다.
- 다른 사용자가 먼저 수정했다면 `409 VERSION_CONFLICT`를 반환한다.
- 편집 잠금이 존재하면 잠금 소유자와 토큰이 일치해야 한다.
- 일괄 작업은 한 건이라도 실패하면 전체를 롤백한다.

## 4. 인증과 세션

### 4.1 회원가입

```text
이름·이메일·비밀번호·약관 동의 입력
→ 이름 길이 검사
→ 이메일 형식과 중복 검사
→ 비밀번호 정책 검사
→ 약관 동의 확인
→ 비밀번호 해시
→ 소속 없는 User 생성
```

- 요청에 `role`이나 `wardId`가 포함되어도 무시한다.
- 회원가입만으로 병동 권한을 부여하지 않는다.
- 생성 후 병동 개설 또는 가입 코드 입력 화면으로 이동한다.

### 4.2 로그인

```text
이메일·비밀번호 입력
→ IP·계정 기준 시도 횟수 검사
→ 사용자 조회
→ 비밀번호 검증
→ 계정 활성 상태 확인
→ 서버 세션 생성
→ 세션 쿠키와 CSRF 쿠키 발급
→ 로그인 감사 로그 생성
```

### 4.3 로그아웃

```text
현재 세션 확인
→ 서버 세션 삭제
→ 세션·CSRF 쿠키 만료
→ 로그아웃 감사 로그 생성
```

## 5. 병동 개설과 가입

### 5.1 병동 개설

```text
로그인 사용자 확인
→ 활성 병동 소속이 없는지 확인
→ 병원명·병동명 검사
→ D/E/N 필요 인원 검사
→ 병동 생성
→ 개설자를 HEAD_NURSE로 등록
→ 개설자의 Nurse 프로필 생성
→ 선택한 규칙 프리셋 복사
→ 가입 코드 발급
→ 감사 로그 생성
```

병동, 소속, 최초 수간호사 프로필, 규칙 세트, 가입 코드 생성은 하나의 트랜잭션으로 처리한다.

### 5.2 병동 가입 신청

```text
가입 코드 입력
→ 코드 형식 검사
→ 계정별 시도 횟수 제한 검사
→ 코드 활성 상태 확인
→ 기존 활성 병동 소속 확인
→ 같은 병동의 PENDING 신청 중복 확인
→ MembershipRequest를 PENDING으로 생성
→ 수간호사에게 알림 생성
```

### 5.3 가입 승인

```text
수간호사 권한 확인
→ 같은 병동의 PENDING 신청인지 확인
→ 신청 계정 활성 상태 확인
→ 기존 미연결 Nurse 후보 조회
→ 기존 프로필 연결 또는 신규 프로필 생성 결정
→ NURSE 역할 Membership 생성
→ 신청을 APPROVED로 변경
→ 신청자에게 승인 알림
→ 감사 로그 생성
```

#### 기존 간호사 연결 기준

- 이름만으로 자동 연결하지 않는다.
- 이름, 입사일, 소속 기간 등으로 후보를 제시한다.
- 최종 연결은 수간호사가 확인한다.
- 연결 대상이 없을 때만 새 Nurse 프로필을 생성한다.

### 5.4 가입 반려

```text
수간호사 권한 확인
→ PENDING 상태 확인
→ 반려 사유 확인
→ REJECTED로 변경
→ 신청자에게 반려 사유 알림
→ 감사 로그 생성
```

### 5.5 수간호사 권한 추가 및 이관

```text
현재 수간호사 권한 확인
→ 대상자가 같은 병동의 활성 간호사인지 확인
→ 대상 Membership과 Nurse 역할을 HEAD_NURSE로 변경
→ 이관이면 기존 수간호사를 NURSE로 변경
→ 병동에 HEAD_NURSE가 최소 한 명인지 확인
→ 감사 로그 생성
```

권한 부여와 강등은 하나의 트랜잭션으로 처리한다.

## 6. 간호사 관리

### 6.1 수간호사 직접 등록

수간호사는 로그인 계정이 없는 간호사도 근무표에 배정할 수 있도록 직접 등록할 수 있다.

```text
수간호사 권한 확인
→ 이름·배정 역할·재직 상태 입력
→ 입사일·경력·숙련도 입력
→ 소속 시작일·종료일 입력
→ 필수값과 날짜 범위 검사
→ 같은 병동의 중복 후보 검사
→ preceptorOf 연결 대상 검사
→ userId=null인 Nurse 프로필 생성
→ 근무표 배정 대상에 포함
→ 감사 로그 생성
```

직접 등록된 간호사는 다음 기능을 사용할 수 있다.

| 기능 | 가능 여부 |
| --- | --- |
| 근무표 배정 | 가능 |
| Excel 출력과 통계 포함 | 가능 |
| 직접 로그인 | 계정 연결 전 불가 |
| 연차·희망 휴무 신청 | 계정 연결 전 불가 |
| 알림 수신 | 계정 연결 전 불가 |

### 6.2 간호사 목록과 상세 조회

```text
병동 구성원 확인
→ 같은 병동 Nurse만 조회
→ 기본적으로 RETIRED 제외
→ 이름·역할·상태 필터 적용
→ 페이지와 정렬 적용
→ 역할에 따라 응답 필드 제거
```

### 6.3 간호사 정보 수정

```text
수간호사 권한 확인
→ 대상 Nurse의 병동 확인
→ version 일치 확인
→ 변경 가능 필드 확인
→ 날짜·경력·숙련도·연결 대상 검사
→ 정보 갱신과 version 증가
→ 관련 DRAFT·CONFIRMED 근무표 재검증
→ 위반 목록 반환
→ 감사 로그 생성
```

- 확정 근무표는 자동 변경하지 않는다.
- 새 위반은 경고로 표시한다.
- 권한 역할 `role`은 권한 이관 API에서만 바꾼다.

### 6.4 퇴사 처리

```text
수간호사 권한 확인
→ 대상 간호사 확인
→ 소속 종료일 검사
→ 마지막 수간호사 여부 확인
→ status=RETIRED와 affiliationEnd 저장
→ 미래 근무표 재검증
→ 감사 로그 생성
```

과거 근무표와 통계 데이터는 삭제하지 않는다.

## 7. 근무 신청

### 7.1 신청 등록

```text
신청자의 활성 병동 소속 확인
→ 연결된 Nurse 프로필 확인
→ 신청 종류 확인
→ 날짜 배열 형식·중복·동일 월 검사
→ 과거 날짜 검사
→ 신청 마감일 검사
→ 소속 기간 검사
→ 확정된 근무표 날짜 검사
→ 기존 PENDING·APPROVED 신청과 날짜 충돌 검사
→ 종류별 월 한도 검사
→ 사유 코드와 상세 사유 검사
→ PENDING 신청 생성
→ 수간호사에게 알림
→ 감사 로그 생성
```

### 7.2 신청 종류별 의미

| 종류 | 의미 | 승인 후 처리 |
| --- | --- | --- |
| ANNUAL_LEAVE | 연차 | 해당 날짜를 반드시 `AL`로 고정 |
| PREFERRED_OFF | 희망 휴무 | 필요 인원을 만족하는 범위에서 `O` 우선 |
| PREFERRED_SHIFT | 희망 근무 | 요청 D/E/N 근무에 우선 배정 |

### 7.3 신청 승인

```text
수간호사 권한 확인
→ PENDING 상태 확인
→ 신청자의 소속과 대상 날짜 재검사
→ 확정 근무표 여부 재검사
→ APPROVED로 변경
→ 종류별 생성 제약 등록
→ 기존 DRAFT 근무표가 있으면 재검증
→ 연차는 해당 셀을 AL로 즉시 반영
→ 신청자에게 승인 알림
→ 감사 로그 생성
```

### 7.4 신청 반려

```text
수간호사 권한 확인
→ PENDING 상태 확인
→ 반려 사유 확인
→ REJECTED로 변경
→ 신청자에게 결과 알림
→ 감사 로그 생성
```

### 7.5 신청 취소

```text
신청자 본인 확인
→ 근무표 확정 전인지 확인
→ PENDING 또는 APPROVED 상태인지 확인
→ CANCELLED로 변경
→ 승인 신청이면 자동 생성 제약 제거
→ 연차이면 DRAFT의 AL 셀을 미배정으로 복원
→ 관련 근무표 재검증
→ 감사 로그 생성
```

REJECTED, CANCELLED 또는 확정된 월의 신청은 다시 취소할 수 없다.

## 8. 근무 규칙

### 8.1 규칙 변경

```text
수간호사 권한 확인
→ 규칙 존재와 병동 확인
→ 변경 가능한 필드 확인
→ 파라미터 허용 범위 검사
→ 필수 HARD 규칙 비활성화 여부 검사
→ 규칙 간 충돌 검사
→ 규칙 저장과 version 증가
→ 모든 DRAFT 근무표 재검증
→ 영향 요약 반환
→ 감사 로그 생성
```

저장된 규칙은 다음 자동 생성과 위반 검사에서 실제로 사용되어야 한다.

### 8.2 HARD 규칙

- 소속 기간 밖 배정 금지
- 임신 간호사 N 금지
- 차지 간호사 E/N 금지
- 신입 간호사 N 단독 배치 금지
- 연속 N 상한
- D/E/N 최소 필요 인원
- 승인된 연차 AL
- 사용자가 고정한 셀

### 8.3 SOFT 규칙

- 희망 휴무와 희망 근무
- 목표 OFF
- 프리셉터와 담당 신입의 동일 근무
- 간호사별 D/E/N 편차
- 주말·공휴일 근무 편차

### 8.4 공휴일과 OFF 목표

```text
공휴일 데이터 조회 또는 수동 변경
→ 변경 날짜 검증
→ 월 OFF 목표 재계산
→ 주말·공휴일 통계 재계산
→ DRAFT 근무표 재검증
→ 감사 로그 생성
```

기본 OFF 목표는 운영 정책으로 관리하며 코드에 고정하지 않는다.

---

## 9. 근무표 생성과 편집

### 9.1 월 근무표 생성

```text
수간호사 권한 확인
→ 대상 연월 검사
→ 같은 달 근무표 존재 여부 확인
→ 대상 월과 소속 기간이 겹치는 간호사 조회
→ 월 날짜 계산
→ 간호사 × 소속 날짜의 null 셀 생성
→ 소속 기간 밖 셀 비활성화
→ 승인된 연차를 AL로 반영
→ DRAFT 근무표 생성
→ 커버리지와 위반 계산
→ 감사 로그 생성
```

동일 월 근무표가 있으면 `409 SCHEDULE_ALREADY_EXISTS`를 반환하고 프론트에서 기존 근무표로 이동한다.

### 9.2 셀 변경

```text
수간호사 권한 확인
→ DRAFT 상태 확인
→ 편집 잠금 확인
→ baseVersion 확인
→ 모든 변경 셀의 병동·간호사·날짜 검사
→ 소속 기간 검사
→ 듀티 코드 검사
→ AL 보호 셀 검사
→ 전체 셀 변경 저장
→ 근무표 version 증가
→ 커버리지·통계·위반 재계산
→ 감사 로그 생성
```

여러 셀 중 하나라도 유효하지 않으면 전체를 롤백한다.

### 9.3 되돌리기와 다시 실행

- 브라우저 편집 세션에서 Undo/Redo 스택을 관리한다.
- Undo/Redo 결과도 일반 셀 변경 API로 서버에 저장한다.
- 새로고침하면 편집 스택을 초기화한다.

---

## 10. 자동 근무표 생성

### 10.1 시작 전 검사

```text
수간호사 권한 확인
→ DRAFT 상태 확인
→ 같은 근무표의 실행 중 작업 확인
→ 활성 간호사와 규칙 세트 확인
→ 고정 셀 존재·소속·날짜·충돌 검사
→ 생성 작업을 QUEUED로 생성
→ 근무표를 GENERATING으로 변경
→ 편집 잠금 설정
```

### 10.2 생성 순서

```text
활성 간호사와 소속 기간 조회
→ 병동 규칙과 필요 인원 조회
→ 승인된 신청 조회
→ AL과 고정 셀을 HARD 제약으로 반영
→ 나머지 HARD 제약을 구성
→ SOFT 제약과 가중치를 구성
→ 유효한 근무표 탐색
→ 공정성과 신청 반영률 최적화
→ 커버리지·통계·위반 전체 계산
```

### 10.3 성공

```text
하드 위반 0건 확인
→ 생성 결과 저장
→ 근무표 version 증가
→ 상태를 DRAFT로 복구
→ 작업 상태 SUCCEEDED
→ 희망 반영률·배정 편차 저장
→ 편집 잠금 해제
→ 감사 로그 생성
```

### 10.4 해 없음

```text
하드 위반이 남아 있음
→ 작업 상태 NO_SOLUTION
→ 충돌 규칙·날짜·필요 인원 분석
→ 완화 가능한 SOFT 조건 제안
→ 최선 부분 결과 별도 저장
→ 근무표 상태 DRAFT 복구
→ 편집 잠금 해제
```

하드 위반이 남은 작업을 `SUCCEEDED`로 처리하지 않는다.

### 10.5 중단

```text
중단 요청 접수
→ 중단 플래그 저장
→ 생성기가 안전한 확인 지점에서 작업 중단
→ 현재 최선 결과 사용 여부 확인
→ STOPPED로 변경
→ 근무표 상태 DRAFT 복구
→ 편집 잠금 해제
```

상태만 `STOPPED`로 바꾸고 백그라운드 작업을 계속 실행해서는 안 된다.

### 10.6 실패

```text
예외 발생
→ FAILED 상태와 오류 코드 저장
→ 근무표 상태 DRAFT 복구
→ 편집 잠금 해제
→ 운영 로그에 jobId와 traceId 기록
```

---

## 11. 커버리지, 위반, 통계

### 11.1 커버리지

날짜별 D/E/N 실제 인원과 필요 인원을 비교한다.

| 상태 | 조건 |
| --- | --- |
| UNDER | 실제 인원 < 필요 인원 |
| MET | 실제 인원 = 필요 인원 |
| OVER | 실제 인원 > 필요 인원 |

### 11.2 위반 검사 시점

- 간호사 정보 변경
- 규칙 변경
- 셀 변경
- 신청 승인 및 취소
- 자동 생성 완료
- Excel 가져오기
- 근무표 확정

각 위반은 `severity`, `ruleId`, `nurseId`, `date`, `currentValue`, `message`, `resolution`을 제공한다.

### 11.3 개인 통계와 공정성

근무표가 변경될 때 다음 값을 다시 계산한다.

- 간호사별 D/E/N/O/AL 횟수
- 목표 OFF와 실제 OFF
- 주말 및 공휴일 근무 횟수
- 연속 근무와 연속 N 일수
- 희망 휴무와 희망 근무 반영률
- 간호사 사이 근무별 배정 편차

수간호사는 병동 전체를 조회하고 일반 간호사는 본인 통계만 조회한다.

## 12. 근무표 확정과 취소

### 12.1 확정

```text
수간호사 권한 확인
→ DRAFT 상태 확인
→ 실행 중 편집·자동 생성 여부 확인
→ 전체 규칙 재검사
→ 하드 위반 0건 확인
→ 소프트 위반 확인 여부 검사
→ CONFIRMED로 변경
→ version 증가
→ 병동 구성원에게 알림
→ 감사 로그 생성
```

일반 간호사는 `CONFIRMED` 또는 `ARCHIVED` 근무표만 조회할 수 있다.

### 12.2 확정 취소

```text
수간호사 권한 확인
→ CONFIRMED 상태 확인
→ 취소 사유 확인
→ DRAFT로 변경
→ 일반 간호사 조회에서 즉시 제외
→ 병동 구성원에게 취소 알림
→ 감사 로그 생성
```

### 12.3 보관

새 기준 월 근무표가 확정되면 이전 확정 근무표를 `ARCHIVED`로 전환한다. 과거 근무표에는 당시 소속 인원과 배정 결과를 유지한다.

## 13. Excel 처리

### 13.1 내보내기

```text
수간호사 권한 확인
→ 근무표 조회
→ 근무 셀·커버리지·개인 통계 구성
→ 듀티별 색상과 인쇄 형식 적용
→ xlsx 생성
→ 정보 반출 감사 로그 생성
→ 파일 반환
```

### 13.2 가져오기

```text
파일 크기·확장자 검사
→ 악성 파일 검사
→ 행·날짜·간호사·듀티 코드 해석
→ 미등록·중복·인식 불가 항목 수집

→ 사용자 매핑 수정

→ baseVersion과 편집 잠금 확인

→ 커버리지·통계·위반 재계산
→ 감사 로그 생성
```

미리보기 단계에서는 실제 근무표를 변경하지 않는다.

## 14. 알림

알림을 생성하기 전에 사용자의 알림 설정을 확인한다.

| 상황 | 대상 |
| --- | --- |
| 병동 가입 승인·반려 | 신청자 |
| 근무 신청 승인·반려 | 신청자 |
| 근무표 확정·확정 취소 | 병동 전체 구성원 |
| 편집 잠금 강제 인수 | 기존 잠금 보유자 |
| 근무 전날 | 해당 근무 간호사 |

- 앱 내 알림 저장을 우선한다.
- 웹 푸시는 별도 전송 실패를 허용한다.
- 알림 전송 실패가 승인이나 확정 트랜잭션을 취소해서는 안 된다.

## 16. 트랜잭션이 필요한 작업

다음 작업은 반드시 하나의 트랜잭션으로 처리한다.

- 병동·최초 소속·최초 수간호사·규칙 세트 생성
- 가입 승인과 Nurse 계정 연결
- 수간호사 권한 이관
- 셀 일괄 변경
- 신청 승인과 AL 반영
- 승인 신청 취소와 제약 제거
- Excel 전체 반영
- 근무표 확정과 알림 대상 생성
- 자동 생성 결과와 작업 상태 저장

트랜잭션 내부 오류가 발생하면 일부 데이터만 남기지 않고 이전 상태로 롤백한다.

## 17. 핵심 운영 수용 기준

- 수간호사가 계정 없는 간호사를 직접 등록하고 근무표에 배정할 수 있다.
- 기존 직접 등록 간호사를 신규 가입 계정과 중복 없이 연결할 수 있다.
- 일반 간호사는 확정 근무표와 본인 데이터만 조회할 수 있다.
- 승인된 연차는 항상 AL로 반영된다.
- 승인된 희망 휴무와 희망 근무는 필요 인원과 HARD 규칙을 침해하지 않는 범위에서 반영된다.
- 저장된 규칙 변경이 다음 검증과 자동 생성에 실제로 적용된다.
- 하드 위반이 남은 자동 생성은 성공으로 처리되지 않는다.
- 하드 위반이 있는 근무표는 확정할 수 없다.
- 다른 병동 ID로 직접 요청해도 데이터가 노출되지 않는다.
- 실패·중단 후 근무표 상태와 편집 잠금이 정상 복구된다.
- 과거 근무표, 퇴사자, 신청, 감사 로그는 상태 기반으로 보존된다.
