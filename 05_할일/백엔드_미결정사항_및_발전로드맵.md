# 백엔드 미결정 사항 및 발전 로드맵

작성일: 2026-11-02
기준: 10/26 클라이언트 회의와 백엔드 PR #85·#86의 구현 (수간호사 로그인 유지, 일반 간호사는 공유 링크 조회)

이 문서는 아직 확정되지 않은 근무 규칙, 운영 전 검증 항목, 이후 발전 과제를 구분한다. 미결정 규칙은 클라이언트 답변 전까지 현재 동작을 유지하되, 답변 후 설정값으로 바꿀 수 있도록 설계하는 것을 원칙으로 한다.

## 1. 의사결정이 필요한 근무 규칙

### 1-1. D/E/N 필요 인원: 최소 인원 또는 정확한 인원

- 현재 동작: D/E/N별 필요 인원을 **최소 인원**으로 처리한다. 부족은 하드 위반이며, 초과 근무는 허용하되 E/N 초과에는 감점을 준다.
- 선택지 A — 최소 인원: `배정 인원 >= 필요 인원`. 갑작스러운 고정 일정이나 O 목표가 있어도 해를 찾기 쉽다.
- 선택지 B — 정확한 인원: `배정 인원 = 필요 인원`. 정원 관리는 명확하지만 남는 인력과 고정 근무 때문에 해 없음이 늘 수 있다.
- 권장 검토안: 최소 인원을 기본으로 두고, 병동 설정에 근무별 최대 인원 또는 `정확히 배정` 옵션을 둔다. 실제 병동이 정확한 정원을 요구하면 해당 옵션을 켠다.
- 클라이언트 확인 질문: “각 근무 인원은 반드시 정확해야 하나요, 아니면 이보다 많아도 괜찮나요? 평일·주말·공휴일의 필요 인원이 같은가요?”
- 확정 후 영향: 커버리지 검증식, 생성 목적함수, 규칙 설정 API, 테스트 시나리오를 함께 변경한다.

### 1-2. 수간호사를 직접간호 필요 인원에 포함할지

- 현재 동작: 수간호사를 평일 D로 배정하고 D 필요 인원에 포함한다.
- 선택지 A — 포함: 근무표상 D 인원으로 계산한다.
- 선택지 B — 제외: 관리 업무 인력으로 표시하되 직접간호 커버리지에는 포함하지 않는다.
- 권장 검토안: 기본은 제외하고, 병동별 `수간호사 커버리지 포함` 설정을 두는 방식을 검토한다. 수간호사의 직접간호 참여 여부가 병동마다 다를 수 있기 때문이다.
- 클라이언트 확인 질문: “수간호사가 D로 표시된 날 실제 환자 담당 인원 한 명으로 계산되나요?”
- 확정 후 영향: 커버리지 집계와 화면 통계만 분리하고, 평일 D/주말 O 표시 규칙은 별도로 유지한다.

### 1-3. 차지 간호사의 추가 O 1일 적용 여부

- 현재 동작: 차지는 평일 D, 주말·공휴일 O이며 일반 간호사의 추가 O 1일은 적용하지 않는다.
- 충돌하는 표현: 회의의 “차지 주5일·주말 휴무”와 “O는 주말+공휴일+1일”이 차지에게 동시에 적용되는지 명확하지 않다.
- 선택지 A — 추가 O 없음: 주5일 기준과 공휴일만 적용한다.
- 선택지 B — 추가 O 있음: 월중 평일에 추가 O 1일을 배정한다.
- 권장 검토안: 클라이언트 확정 전까지 현재 동작을 유지하고, `차지 추가 O`를 병동 설정으로 분리한다.
- 클라이언트 확인 질문: “주말과 공휴일 외의 추가 O 1일이 차지 간호사에게도 적용되나요?”
- 확정 후 영향: 차지 O 목표, 평일 D 하드 규칙, 커버리지 가능 여부를 함께 재검증한다.

### 1-4. 중도 입·퇴사자의 O 계산

- 현재 동작: 월 O 목표에 해당 월 소속 일수 비율을 곱해 반올림한다.
- 선택지 A — 현재 방식: `월 O 목표 × 소속 일수 ÷ 월 일수`. 구현과 설명이 단순하다.
- 선택지 B — 실제 달력 방식: 소속 기간 안의 주말·공휴일을 직접 세고, 추가 O 1일만 소속 기간에 따라 적용한다.
- 권장 검토안: 실제 달력 방식이 현장 설명에 더 가깝다. 예를 들어 월 중순 입사자가 실제로 포함하는 주말과 공휴일을 그대로 계산할 수 있다.
- 클라이언트 확인 질문: “월 중간 입사·퇴사자는 실제 재직 기간의 주말/공휴일을 세나요, 월 전체 O를 일할 계산하나요? 추가 O 1일은 며칠 이상 근무해야 받나요?”
- 확정 후 영향: O 목표 계산 함수, 통계, 중도 소속 테스트를 변경한다. 이미 확정한 과거 근무표는 다시 계산하지 않는다.

## 2. 공휴일 자동 연동

### 현재 상태

- 양력 고정 공휴일과 병동 관리자가 입력한 보정값을 사용한다.
- 설·추석·대체·임시공휴일은 관리자가 직접 입력해야 한다.
- 관리자의 보정값은 자동 데이터보다 우선해야 한다.

### 발전 단계

1. 사용할 공식 공휴일 데이터 출처와 인증 방식, 이용 한도를 결정한다.
2. 연도별 공휴일을 미리 가져와 DB에 캐시하고 출처·가져온 시각을 저장한다.
3. 자동 데이터 위에 병동별 추가/제외 보정을 덮어쓴다.
4. 동기화 실패 시 마지막 정상 데이터와 수동 입력을 계속 사용한다.
5. 연말에 다음 연도 데이터를 사전 동기화하고, 임시공휴일 발표 시 재동기화할 수 있게 한다.
6. 중복 공휴일, 주말과 겹치는 공휴일, 대체공휴일을 합집합으로 계산하는 테스트를 둔다.

완료 기준은 특정 월의 공휴일 원본과 병동 보정 결과를 조회할 수 있고, 외부 연동 장애가 근무표 조회·생성을 막지 않는 것이다.

## 3. PostgreSQL 및 운영 데이터 전환 검증

이 작업은 클라이언트의 근무 규칙 답변을 기다리지 않고 진행할 수 있다.

### 사전 준비

- 운영 DB와 같은 PostgreSQL 버전의 스테이징 환경을 만든다.
- 운영 데이터가 있다면 개인정보를 가린 복제본을 사용한다.
- 마이그레이션 직전 전체 백업을 만들고 실제 복구가 되는지 확인한다.
- 현재 시작 시 실행되는 보정 코드 대신 버전이 명확한 정식 마이그레이션 도구를 도입한다.

### 검증 항목

- `is_preceptor`, 공유 링크 관련 스키마와 인덱스 생성 여부
- `link-head-account`로 기존 병동의 합성 사용자가 수간호사 실계정으로 정확히 바뀌는지
- 기존 PRECEPTOR 값이 GENERAL + `is_preceptor=true`로 정확히 전환되는지
- 기존 입사일, 소속 기간, 간호사 수, 근무표 셀 수, 확정 상태가 유지되는지
- 공유 링크 원문이 DB나 로그에 저장되지 않고 해시만 남는지
- 동일 월 근무표 생성, 링크 교체, 셀 버전 충돌 등의 동시 요청이 한 번만 반영되는지
- PostgreSQL에서 전체 테스트와 대표 API 시나리오가 통과하는지
- 마이그레이션 실패 시 백업 복구와 이전 버전 서비스 재기동이 가능한지

### 완료 산출물

- 실행·복구 절차서
- 전환 전후 행 수와 주요 필드 비교 보고서
- PostgreSQL 테스트 결과
- 실제 전환 예상 시간과 서비스 중단 필요 여부

## 4. 실제 병동 조건 다개월 생성 검증

단일 성공 사례 대신 재현 가능한 시나리오 묶음으로 생성 품질을 측정한다.

### 시나리오 구성

- 28·29·30·31일 달, 평년과 윤년
- 평일 공휴일이 0개인 달부터 명절·대체공휴일이 포함된 달
- 수간호사 1, 차지 2, 일반 25를 기본으로 결원·증원 조합
- 신규·프리셉터·임신·휴직·나이트 전담·중도 입퇴사 조합
- 연차·교육·학회·종이 달력 O 및 수동 고정 셀 조합
- 이전 달 말의 D/E/N/O 패턴을 포함한 월 경계 조건
- 충분한 인력의 정상 입력과, 의도적으로 해가 없는 입력을 분리

### 측정 지표

| 영역 | 지표와 임시 수용 기준 |
|---|---|
| 필수 규칙 | 정상 시나리오의 하드 위반 0, 필요 인원 부족 0 |
| 고정 일정 | AL·ED·고정 셀 보존율 100% |
| O | 대상별 목표 일치, 차지·수간호사 규칙 위반 0 |
| 편중 | 같은 조건의 일반 간호사끼리 E/N 횟수 최대-최소 차이 2회 이내를 우선 기준으로 측정 |
| 패턴 | 금지 역순환, 최대 연속 근무·야간, 야간 후 휴식 위반 0 |
| 성능 | 생성 시간 평균·중앙값·p95와 제한시간 초과율 기록 |
| 성공률 | 정상 시나리오 성공률, 해 없음 입력의 원인 설명 성공률을 별도 기록 |
| 안정성 | 같은 입력의 반복 결과 품질 편차와 실패 재현 가능 여부 기록 |

편중 기준 2회와 생성 제한시간은 내부 검증 기준이며, 실제 병동 사례를 받은 뒤 클라이언트와 확정한다. 이름별 결과만 비교하지 않고 경력·역할·근무 제한이 같은 그룹끼리 비교한다.

### 결과 보고서

- 월별 성공/실패와 실패 원인
- 간호사별 D/E/N/O·주말·공휴일 근무 분포
- 가장 많이/적게 배정된 사람과 차이의 원인
- 규칙별 위반·완화 횟수
- 생성 시간 분포와 제한시간 초과 사례
- 실패 입력을 다시 실행할 수 있는 익명화된 입력 스냅샷

## 5. 추후 발전이 필요한 백엔드 사항

### P0 — 운영 전 필수

- 정식 DB 마이그레이션 도입과 PostgreSQL 전환·복구 리허설
- PR마다 PostgreSQL 포함 전체 테스트를 실행하는 CI
- 수간호사 비밀번호 분실 시 운영자가 안전하게 재설정하는 절차
- 세션 쿠키·CSRF 토큰·공유 토큰의 로그·오류 응답·분석 도구 노출 방지 점검
- 배포 환경 백업, 상태 확인, 오류 추적, 감사 로그 보관 정책
- 1~4번 미결정 규칙을 병동 설정으로 분리하고 결정 이력을 감사 로그에 남기기

### P1 — 생성 품질과 운영성 개선

- 다개월 시뮬레이션 도구와 품질 리포트 자동 생성
- 이전 달뿐 아니라 최근 여러 달의 E/N·주말 근무 이력을 반영한 장기 공정성
- 평일·주말·공휴일별 필요 인원과 날짜별 특별 필요 인원 설정
- 해가 없을 때 충돌한 규칙·날짜·인원을 더 구체적으로 설명하는 기능
- 생성 결과 비교, 버전 보관, 이전 결과 복원
- 공휴일 자동 동기화와 관리자 보정 이력
- 생성 시간, 성공률, 하드 위반 수, 편중 지표 모니터링

### P2 — 규모 확장과 보안 강화

- 생성 작업을 백그라운드 큐로 전환하고 실제 진행률·중단·재시도 제공
- 공유 링크의 선택적 만료일, 사용 중지, 접근 이력
- 공개 근무표의 이름 노출 범위와 익명 표시 옵션
- API 요청 제한, 비정상 토큰 시도 탐지, 키 교체 정책
- 여러 병동·병원 단위 관리와 규칙 템플릿 복제
- 제거된 일반 간호사 계정·신청 데이터의 보존 기간과 최종 삭제 정책

## 6. 권장 진행 순서

1. 클라이언트에게 1~4번 규칙을 질문하고 결정 기록을 남긴다.
2. 답변을 기다리는 동안 PostgreSQL 마이그레이션·CI·백업/복구 검증을 진행한다.
3. 7번 다개월 시뮬레이션을 자동화하고 현재 구현의 기준 결과를 만든다.
4. 결정된 규칙을 설정화한 뒤 동일 시나리오를 다시 실행해 결과를 비교한다.
5. 공휴일 자동 연동을 추가하고 외부 연동 장애 시 동작을 검증한다.
6. P0를 모두 통과한 뒤 운영 데이터 전환과 배포 여부를 결정한다.

## 7. 완료 판단

백엔드가 운영 준비 완료로 판단되려면 다음을 모두 만족해야 한다.

- 1~4번 도메인 규칙에 클라이언트 결정이 기록되어 있다.
- 실제 PostgreSQL에서 마이그레이션과 복구가 검증되었다.
- 대표 병동 시나리오의 다개월 생성 결과가 합의한 품질 기준을 통과한다.
- 공휴일 데이터 누락 시 보정 절차가 마련되어 있다.
- CI, 백업, 오류 추적, 수간호사 계정 복구 절차가 준비되어 있다.
