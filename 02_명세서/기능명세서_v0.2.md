## 1. 공통 정의 (COM)

### COM-01. 역할 · 권한 매트릭스 **[신규]**

**역할은 계정 속성이 아니라 병동 소속의 속성이다.** 한 계정이 여러 병동에 소속될 경우 병동별로 역할을 가진다. 🔶 (다중 병동 소속 허용 여부 확인 필요)

| 역할 | 설명 |
|---|---|
| `HEAD_NURSE` | 수간호사. 병동 관리 권한 보유 |
| `NURSE` | 일반 간호사 |

> **차지 / 프리셉터 / 신입 / 일반(NUR-05)은 권한이 아니라 배정 규칙용 속성이다.** 권한 역할과 혼동하지 않는다. 문서 전체에서 전자는 `duty_role`, 후자는 `role`로 구분한다.

| 기능 | HEAD_NURSE | NURSE |
|---|---|---|
| 병동 개설 (AUTH-00) | ○ (개설자가 자동으로 수간호사) | ○ |
| 병동 코드 발급·재발급 (AUTH-04) | ○ | ✕ |
| 가입 승인·반려 (AUTH-06) | ○ | ✕ |
| 간호사 목록 조회 (NUR-03) | 전체 필드 | 이름·역할·소속 기간만 |
| 간호사 등록·수정·퇴사 (NUR) | ○ | ✕ |
| 규칙 설정 (RULE) | ○ | ✕ |
| 근무표 생성·편집 (SCH) | ○ | ✕ |
| 근무표 조회 — 초안 | ○ | **✕ (확정본만)** |
| 근무표 조회 — 확정본 (REQ-05) | ○ | ○ (숨김 항목 적용) |
| 개인별 통계 (SCH-10) | 전원 | **본인만** |
| 근무 부담 분석 | 전원 | **본인만** |
| 감사 로그 조회 (SEC-02) | 본인 병동만 | ✕ |
| 엑셀 내보내기 (SCH-09) | ○ | ✕ |
| 연차·희망오프 신청 (REQ) | ○ | ○ |
| 본인 신청 내역 조회 (REQ-07) | ○ | ○ |

**일반 간호사에게 숨기는 항목** (REQ-05·SCH-08·NUR-03 공통)

- 타인의 숙련도 · 경력
- 타인의 연차 · 희망오프 사유
- 타인의 상태(임신 등)
- 편집 중인 초안 근무표 전체
- 감사 로그 전체

### COM-02. 간호사 엔티티 정의 **[신규]**

> v0.1에는 엔티티 정의가 없어 등록과 수정이 서로 다른 필드셋으로 구현되었다. 아래를 단일 기준으로 삼는다.

| 필드 | 타입 | 필수 | 등록 시 | 수정 가능 | 설명 |
|---|---|---|---|---|---|
| `name` | string | ○ | ○ | ○ | 이름 |
| `role` | enum | ○ | ○ | ○ | `HEAD_NURSE` / `NURSE` (COM-01) |
| `dutyRole` | enum | ○ | ○ | ○ | `CHARGE` / `PRECEPTOR` / `NEW` / `GENERAL` (NUR-05) |
| `status` | enum | ○ | ○ | ○ | `ACTIVE` / `PREGNANT` / `ON_LEAVE` / `RETIRED` |
| `joinedAt` | date | ○ | ○ | ○ | 입사일 |
| `careerMonths` | int | ○ | ○ | ○ | 총 경력(개월). 입사일과 별개 — 경력직 입사 대응 |
| `skillLevel` | int 1–5 | ○ | ○ | ○ | 숙련도. 수간호사만 조회 가능 |
| `affiliationStart` | date | ○ | ○ | ○ | 소속 시작일 (NUR-08) |
| `affiliationEnd` | date | ✕ | ✕ | ○ | 소속 종료일. null이면 재직 중 |
| `preceptorOf` | id[] | ✕ | ✕ | ○ | 프리셉터인 경우 담당 신입 |

**제거된 필드** — v0.1 API에 있었으나 기능 명세에 근거가 없어 삭제한다.<br>`position`(→ `role`·`dutyRole`로 분리), `team`, `shiftType`

**규칙**

- 등록 시 입력한 필드는 모두 수정 가능해야 한다. 등록 전용 / 수정 전용 필드를 두지 않는다.
- `skillLevel`은 일반 간호사 응답에서 제외한다 (COM-01).

### COM-03. 듀티 코드 정의 **[신규]**

| 코드 | 명칭 | 비고 |
|---|---|---|
| `D` | Day |  |
| `E` | Evening |  |
| `N` | Night |  |
| `O` | Off | 비번 |
| `AL` | 연차 | REQ-01 승인 시 자동 입력. 수동 입력 불가 |
| `ED` | 교육 | 🔶 사용 여부 확인 필요 |

- 셀의 빈 값(`null`)은 **미배정**이며 `O`와 구분한다. 커버리지 계산에서 미배정은 인원으로 세지 않는다.
- 엑셀 가져오기(SCH-11)의 코드 매핑 테이블은 위 코드를 목표값으로 한다.

### COM-04. 근무표 상태 전이 **[신규]**

```text
DRAFT ──(GEN-01 실행)──> GENERATING ──(완료/중단)──> DRAFT
  │
  └──(SCH-12 확정)──> CONFIRMED ──(SCH-12 확정 취소)──> DRAFT
                          │
                          └──(다음 달 확정 시)──> ARCHIVED (읽기 전용, SCH-08)
```

| 상태 | 편집 | 일반 간호사 조회 | 비고 |
|---|---|---|---|
| `DRAFT` | ○ | **✕** | 초안 |
| `GENERATING` | ✕ (잠금) | ✕ | 자동 생성 진행 중 |
| `CONFIRMED` | △ (확정 취소 후에만) | ○ | 확정본 |
| `ARCHIVED` | ✕ | ○ | 과거 근무표 |

## 2. 인증 · 소속 (AUTH)

### AUTH-00. 병동 개설 · 최초 수간호사 **[신규]**

> **v0.1의 구멍:** AUTH-01은 "계정 생성(소속 없음) → AUTH-03 병동 코드 입력"인데, 코드를 발급하는 수간호사가 최초에 어떻게 생기는지 정의되지 않았다. 이 때문에 API 구현에서 회원가입 body로 `role`을 받는 권한 상승 결함이 발생했다.

| 항목 | 내용 |
|---|---|
| **설명** | 소속이 없는 사용자가 새 병동을 개설하고 그 병동의 수간호사가 된다 |
| **입력** | 병동명, 병원명, 듀티별 필요 인원(COM-03 기준 D/E/N 각각), 규칙 프리셋 선택(RULE-05) |
| **처리** | ① 병동 생성 ② **개설자를 해당 병동의 `HEAD_NURSE`로 등록** ③ 병동 코드 자동 발급(AUTH-04) ④ 감사 로그 기록 |
| **출력** | 병동 생성 완료 + 코드 문자열 → 근무표 생성 화면 |
| **예외** | 이미 소속이 있는 사용자는 개설 불가 🔶 (겸직 허용 여부에 따라 달라짐) |
| **권한** | 소속 없는 로그인 사용자 |
| **보안** | **역할은 이 기능과 AUTH-06으로만 부여된다. 가입 입력으로 역할을 받지 않는다.** |

### AUTH-01. 회원가입 **[수정]**

| 항목 | 내용 |
|---|---|
| **설명** | 신규 사용자가 계정을 생성한다 |
| **입력** | 이름, 이메일, 비밀번호, 약관 동의 |
| **처리** | ① 이메일 중복 확인 ② 비밀번호 해시 저장 ③ 계정 생성(소속 없음 상태) ④ 소속 선택 화면으로 이동 |
| **출력** | 계정 생성 완료 → **소속 선택 화면 (병동 코드 입력 / 병동 개설 중 택1)** |
| **예외** | 이메일 중복 / 비밀번호 규칙 미달(8자 이상, 영문+숫자) / 약관 미동의 |
| **보안** | **역할(role)·병동 ID를 입력으로 받지 않는다.** 클라이언트가 보내더라도 서버는 무시한다 |
| **비고** | 주민등록번호·생년월일·주소는 수집하지 않는다 |

### AUTH-02. 소셜 로그인 🔶

| 항목 | 내용 |
|---|---|
| **설명** | 외부 계정으로 가입·로그인한다 |
| **입력** | 소셜 제공자 선택 → 외부 인증 |
| **처리** | ① 인증 성공 시 프로필(이름, 이메일) 수신 ② 기존 계정 있으면 연결, 없으면 신규 생성 ③ 소속 없으면 소속 선택 화면으로 이동 |
| **출력** | 로그인 완료 |
| **예외** | 인증 취소 / 이메일 미제공 시 수동 입력 요구 |
| **보안** | AUTH-01과 동일 — 역할을 입력으로 받지 않는다 |
| **비고** | 🔶 제공자(카카오/구글) 확정 필요. 소셜 계정에서 받은 정보 외 추가 수집 없음 |

### AUTH-03. 병동 코드 입력 · 가입 신청 **[신규]**

> v0.1에서 AUTH-01·02·06이 참조하기만 하고 정의가 없던 항목이다.

| 항목 | 내용 |
|---|---|
| **설명** | 소속 없는 사용자가 병동 코드를 입력해 가입을 신청한다 |
| **입력** | 병동 코드 (영숫자 6~8자) |
| **처리** | ① 코드 유효성 확인(활성 코드인지) ② 병동 조회 ③ `승인 대기` 상태로 가입 신청 등록 ④ 수간호사 대기 목록에 노출(AUTH-06) ⑤ 감사 로그 기록 |
| **출력** | 신청 완료 → 승인 대기 화면 |
| **예외** | 존재하지 않는 코드 / **비활성화된 코드(재발급으로 폐기됨)** / 이미 해당 병동에 신청·소속됨 |
| **보안** | **코드 무차별 대입 방지: 계정당 시도 횟수 제한 🔶 (권장 10회/시간)** |
| **비고** | AUTH-06이 불필요로 결정되면 ③에서 즉시 `NURSE`로 소속 확정한다 |

### AUTH-04. 병동 코드 발급 · 재발급

| 항목 | 내용 |
|---|---|
| **설명** | 수간호사가 병동 가입용 코드를 발급·관리한다 |
| **입력** | (발급) 없음 — 대상 병동은 요청자의 소속 병동 / (재발급) 없음 |
| **처리** | ① 영숫자 6~8자 코드 생성 ② 기존 코드가 있으면 비활성화 후 신규 발급 ③ 감사 로그 기록 |
| **출력** | 코드 문자열 + 복사 버튼 |
| **예외** | 재발급 시 기존 코드로는 더 이상 가입 불가 (이미 소속된 인원에는 영향 없음) |
| **권한** | 수간호사 |
| **비고** | **[수정]** v0.1은 발급 입력이 "병동명"이었으나, 병동은 이미 존재하므로 병동명을 입력받지 않는다 |

### AUTH-05. 세션 관리 · 로그아웃 **[수정]**

| 항목 | 내용 |
|---|---|
| **설명** | 로그인 상태를 유지하고 종료한다 |
| **처리** | ① 로그인 시 토큰 발급 ② 만료 시 재로그인 요구 ③ 로그아웃 시 토큰 무효화 ④ 로그인·로그아웃 감사 로그 기록 |
| **보안** | 액세스·리프레시 토큰 모두 `HttpOnly` `Secure` `SameSite` 쿠키로 전달한다. **토큰을 요청 본문(body)이나 쿼리스트링으로 주고받지 않는다.** 자동 로그아웃 시간 🔶 (권장: 액세스 30분 / 리프레시 14일) |
| **예외** | 만료된 토큰으로 API 호출 시 401 반환 후 로그인 화면 이동 |

### AUTH-06. 가입 승인 🔶

| 항목 | 내용 |
|---|---|
| **설명** | 병동 코드로 가입 신청한 사용자를 수간호사가 승인한다 |
| **처리** | ① AUTH-03에서 `승인 대기` 등록 ② 수간호사에게 대기 목록 노출 ③ 승인 시 `NURSE`로 소속 확정, 반려 시 제거 ④ 감사 로그 기록 |
| **출력** | 승인 완료 후 근무표 조회 가능 |
| **권한** | 수간호사 |
| **보안** | **승인으로 부여되는 역할은 `NURSE`로 고정한다.** 수간호사 권한 부여는 AUTH-07로만 가능 |
| **비고** | 🔶 이 단계가 필요한지 확인 필요. 불필요하면 AUTH-03에서 즉시 소속 처리 |

### AUTH-07. 수간호사 권한 이관 **[신규]**

### GEN-01. 자동 생성 실행 **[신규]**

| 항목 | 내용 |

## 7. 신청 (REQ)

> REQ-01(연차) · REQ-03(승인·반려) · REQ-04는 v0.1 원본 유지.<br>**[추가 요구]** 연차·희망오프·희망근무는 **하나의 신청(Request) 리소스로 통합**하고 `type`으로 구분한다. 승인·조회·취소 흐름을 공통화하기 위함이다.

### REQ-02. 희망 오프 신청 **[수정]**

| **비고** | 미반영이 누적된 인원은 다음 달 우선순위를 높인다 (공정성) |

| 항목 | 내용 |

| **출력** | 읽기 전용 그리드. 모바일에서는 축약 형태 |

| **비고** | 숨김은 서버에서 필드를 제외해 처리한다. 클라이언트에서 가리는 방식은 금지 |

### SEC-03. 접근 통제 원칙 **[신규]**

> API 명세 검토에서 병동 범위 우회(IDOR) 가능성이 발견되어 원칙으로 명문화한다.

| 항목 | 내용 |
|---|---|
| **원칙 1** | **요청에 포함된 병동·간호사·근무표 식별자는 신뢰하지 않는다.** 서버는 모든 요청에서 "요청자의 소속 병동"과 대상 리소스의 병동이 일치하는지 검증한다 |
| **원칙 2** | 불일치 시 403이 아닌 **404를 반환한다.** 403은 "그 병동이 존재한다"는 정보를 노출한다 |
| **원칙 3** | 역할은 요청 본문으로 받지 않는다. 서버가 세션에서 판정한다 (AUTH-01·06) |
| **원칙 4** | 응답 필드 차등(COM-01)은 서버에서 적용한다. 클라이언트 숨김으로 대체하지 않는다 |
| **원칙 5** | 병동 범위가 없는 전역 조회 API(전체 사용자 목록 등)는 제공하지 않는다 |
| **원칙 6** | 본인 리소스 조회는 식별자 대신 `me`를 사용한다. 타인 식별자를 넣어 조회할 수 있는 경로를 만들지 않는다 |
| **검증** | 위 원칙은 기능별 서술이 아니라 **전역 요구사항**이며, 모든 엔드포인트에 예외 없이 적용된다 |
