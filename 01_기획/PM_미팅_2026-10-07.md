## 회의 개요

- **성격**: 주간 실적 점검 및 시연 리뷰 (선생님 피드백)
- **참석**: 선생님, 이석찬, 최수혁 외 팀원 (받아쓰기상 화자 약 9명)
- **결론 한 줄**: 기능 시연보다 **데이터 설계와 코드 리뷰 문화**가 먼저다. 팀 문화를 다시 정리할 것.

## 주요 논의

### 1. 주간 실적 점검: 프론트 코드 커밋 제로

- 일주일 실적을 커밋 수치 기준으로 점검했어요.
- 디자인 담당이 프론트 화면까지 맡은 상황이에요. 프론트 담당(이석찬)의 프론트 코드 커밋은 0건이었고, 백엔드 담당(최수혁)의 커밋도 함께 지적됐어요.
- 선생님: "실적은 수치로 나올 수 있는 것까지 따져봐야 한다."

### 2. 시연 내용

- 근무표를 **주간 / 월별**로 분리해 보기 쉽게 개선
- **사용자 추가(간호사 등록)** 기능, 역할(role) 구분 적용

### 3. 간호사 명단 테이블 vs 유저 테이블 매칭 (미결)

- 수간호사가 직접 등록하는 **간호사 명단** 테이블과, 간호사가 회원가입·로그인해서 생기는 **유저** 테이블이 따로 있어요.
- 선생님 질문: 수간호사가 근무표를 짤 때 신청은 가입한 간호사(유저)가 하는데, 이 둘을 **어떻게 매칭할 것인가?**
- 팀 답변: 가입·신청 시 연차 등 정보를 입력받아 맞추기로 했던 것 같다 → 명확한 설계 없음
- 선생님: "DB 설계를 머릿속에 그려보고 답이 나와야 한다. 그냥 추가만 되는 건 '딸깍'에 불과하다."

### 4. 코드 리뷰 프로세스 미이행

- 원래 합의: PR 작성자를 제외한 3명 중 **최소 1명이 코멘트**를 남기기로 함 (제1원칙)
- 실제: AI 자동 리뷰만 있고 팀원 리뷰 코멘트가 없음
- PR이 한 번에 약 13개 올라와 당황스러웠다는 의견이 있었어요. 이석찬이 기능 단위로 이슈와 PR을 나눠 달라고 요청했기 때문이에요.
- 선생님 피드백:
	- PR을 잘게 나누는 건 팀 스타일이니 괜찮다. 대신 혼자 다 볼 수 없으니 **세 명이 나눠서 리뷰**해야 한다.
	- 시연만 보면 클라이언트는 "오케이" 하지만, 실제로 쓸 때 에러가 난다.
	- 코드를 직접 안 쓸 거라면 **최소한 읽고 리뷰는 해야** 한다. AI에 다 맡길 거면 채용할 이유가 없다.

## 결정 사항
